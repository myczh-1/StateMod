## C：类型文字改变与内部状态影响分开

仅固定一个真实 V 退化反例：literal_a_occurrences_E_W_INTERFACE。使用原 Prompt 和历史实际 return 前缀，在相同原生缓存检查点分叉。

再做以下四个诊断分支：

|分支|原 return 决策步 Bank|随后固定构造器 Token|构造器之后|
|---|---|---|---|
|OFF_SET|关闭|` set`|无 Bank 贪心续写|
|OFF_FRO|关闭|` frozenset`|无 Bank 贪心续写|
|ON_SET|原强度，只一次|` set`|无 Bank 贪心续写|
|ON_FRO|原强度，只一次|` frozenset`|无 Bank 贪心续写|

共6个分支。其中4条固定构造器分支不是自然生成，不能计入实际自主选类型或 AUTO 成绩。只固定构造器，不提供参数、括号或正确计数代码。特别不强制左括号，因为原失败的 `(count` 是一个 Token，提前给 `(` 会移除需要研究的选择。

实现语义必须明确：

1. 从相同、未修改的 pre-onset 检查点处理当前 return 末 Token，分别获得 OFF/ON Logits及原生缓存。
2. 忽略该步采样结果，按预冻结 Token ID 输入指定构造器；所有后续步 Bank 关闭。不得从另外一个条件复制构造器阶段的缓存。
3. 处理完构造器末 Token后开始真正贪心续写。相同构造器的 ON/OFF 两条拥有完全相同 Token 历史，可比较 Logits和缓存状态。
4. 强制 Token 计入原96 Token预算；保留原生成前缀的预算消耗。不通过额外预算帮助任何分支。
5. Fresh 从原输入开始，严格重放相同强制 Token 和唯一注入历史；不能用全程无 Bank Fresh 验证 ON。

主要对比：

- OFF_FRO vs OFF_SET：无 Bank 时，换成该构造器 Token 历史是否已足以诱发参数错误。包含构造器长度/位置差异，不能称纯语义影响。
- ON_FRO vs OFF_FRO：相同 frozenset Token 历史下，原单步干预留下的计算历史是否改变参数选择或功能。若只有 ON 错，支持内部状态贡献。
- ON_SET vs OFF_SET：强制保留 set 后，内部干预是否仍损害计算。
- ON_FRO vs 自然 ON：若自然 ON 确实选完整 frozenset，这两条按相同 Token 历史应重现；OFF_SET 同理。差异首先视为工程问题。
